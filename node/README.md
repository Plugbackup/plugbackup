# Нода хранения

Всё, что нужно на ноде, чтобы бот выдавал клиентам место: скрипт `storectl`, примеры настроек sshd и sudo, снимки через sanoid. Установка ZFS, nftables и WireGuard здесь пока не описаны.

> Раскладка каталогов ниже выбрана мной, потому что готового `storectl` в репозитории не было. Если на вашей ноде всё устроено иначе, правятся только значения в `storectl.conf` и пути в примерах.

Адреса в примерах взяты из диапазона для документации (`192.0.2.0/24`). Подставьте свои.

## Как устроена нода

```
VPS с ботом ──WireGuard──► нода
                           ├─ пользователь provision: SSH-ключ бота, только storectl --ssh
                           ├─ sshd: клиенты запираются в chroot и получают только SFTP
                           └─ ZFS: tank/clients/<логин>, квота refquota на клиента
```

| Что | Где |
| --- | --- |
| ZFS-набор клиента | `tank/clients/u1001` (родитель задаётся `ZFS_PARENT`) |
| Корень chroot клиента | `/srv/plugbackup/u1001`, владелец root, права 0755 |
| Данные клиента | `/srv/plugbackup/u1001/data`, владелец клиент, права 0700 |
| Что видит клиент | `/data`, репозиторий restic: `sftp:<хост>:/data/restic` |
| Ключ клиента | `/etc/plugbackup/authorized_keys.d/u1001`, владелец root |
| Ключ заблокированного | `/etc/plugbackup/suspended.d/u1001` |
| Системный пользователь | `u1001`, uid = `UID_BASE` + 1001, оболочки нет |

Логин `u1001` — это `u` и число. Первым клиентом бота будет `u1001`, вторым `u1002`, и так далее.

## Установка

Команды выполняются от root.

**1. Группа и каталоги.**

```bash
groupadd --gid 30000 plugbackup-clients
install -d -m 0755 /etc/plugbackup /etc/plugbackup/authorized_keys.d /etc/plugbackup/suspended.d
install -d -m 0755 /srv/plugbackup
zfs create -o mountpoint=none tank/clients
```

**2. Скрипт и настройки.**

```bash
install -m 0755 -o root -g root node/storectl /usr/local/sbin/storectl
install -m 0644 node/storectl.conf.example /etc/plugbackup/storectl.conf
```

Значения по умолчанию подходят, если набор называется `tank/clients`. Иначе поправьте `ZFS_PARENT` в `/etc/plugbackup/storectl.conf`.

**3. Секрет для хешей IP.** Нужен только команде `logins`. Он остаётся на ноде и в бота не попадает.

```bash
head -c 32 /dev/urandom | xxd -p -c 64 > /etc/plugbackup/ip-hmac.key
chmod 0600 /etc/plugbackup/ip-hmac.key
```

Если секрет заменить, все прежние хеши перестанут совпадать, и алерт «новый IP» заново выучит адреса клиентов.

**4. Пользователь provision.** Бот заходит под ним по SSH и может запускать только `storectl`.

```bash
useradd --create-home --shell /bin/bash provision
install -d -m 0700 -o provision -g provision /home/provision/.ssh
install -m 0440 node/sudoers-provision.example /etc/sudoers.d/plugbackup-provision
visudo -cf /etc/sudoers.d/plugbackup-provision
```

В `/home/provision/.ssh/authorized_keys` положите одну строку с публичным ключом бота. `from` ограничивает вход адресом VPS в WireGuard-сети:

```
restrict,command="sudo -n /usr/local/sbin/storectl --ssh",from="192.0.2.2" ssh-ed25519 <публичный ключ бота>
```

Пара ключей создаётся на VPS, приватная часть остаётся там (`SSH_KEY_PATH` в `.env` бота). Отпечаток ключа ноды добавьте в `known_hosts` бота заранее: бот подключается с `StrictHostKeyChecking=yes`.

**5. sshd для клиентов.**

```bash
install -m 0644 node/sshd-plugbackup.conf.example /etc/ssh/sshd_config.d/plugbackup.conf
sshd -t && systemctl reload ssh
```

**6. Снимки.**

```bash
apt install sanoid
install -d /etc/sanoid
install -m 0644 node/sanoid.conf.example /etc/sanoid/sanoid.conf
systemctl enable --now sanoid.timer
```

Раз в сутки появляется снимок каждого клиентского набора, хранятся семь последних.

**7. Проверка вручную.**

```bash
storectl add u1001 1G "<тело ключа ed25519>"
storectl usage u1001
storectl suspend u1001
storectl resume u1001
storectl delete u1001
```

## Команды

| Команда | Что делает |
| --- | --- |
| `add <login> <N>G <ключ>` | Создаёт клиента: пользователь, ZFS-набор с `refquota`, каталог `data`, ключ. Если клиент есть, обновляет ключ и квоту. Повтор безопасен. Заблокированный клиент остаётся заблокированным |
| `resize <login> <N>G` | Меняет `refquota`. Ниже занятого места нельзя |
| `suspend <login>` | Убирает ключ из активных, обрывает сессии. Данные остаются |
| `resume <login>` | Возвращает ключ |
| `delete <login>` | Обрывает сессии, удаляет ключи, набор со всеми снимками и пользователя. Если клиента уже нет, это успех |
| `usage <login>` | Две строки: занято и квота, в байтах |
| `logins <login> <since>` | События входа с unix-времени `since`, см. ниже |

Ключ передаётся только телом без префикса: `AAAAC3NzaC1lZDI1NTE5...`. Хранится в файле как `restrict ssh-ed25519 <тело>`.

**Коды выхода.** `0` успех, `2` неверные аргументы, `3` клиента нет, `4` конфликт, `5` квота ниже занятого места, `6` внутренняя ошибка. Бот повторяет операцию только при `6` и при сбое связи.

**Что значит «занято».** `usage` отдаёт свойство `referenced`, а не `used`: квота `refquota` ограничивает именно его, а `used` включает ещё и снимки. Поэтому место, занятое снимками, клиенту не засчитывается.

**Проверка аргументов.** Логин: `u` и от 4 до 9 цифр. Квота: от `1G` до `100000G`. Ключ: регулярка `^AAAAC3NzaC1lZDI1NTE5[A-Za-z0-9+/=]+$`, затем разбор blob (ровно ed25519, 32 байта ключа). Любое другое значение даёт код 2 до того, как выполнится хоть одна команда. Внешние программы запускаются списком аргументов, без оболочки. Имена наборов и путей строятся только из проверенного логина.

## Команда `logins`

```
storectl logins u1001 1793600000
1793600120 ok 3f9a1c5e07b2d481
1793600150 fail 0b7e44d2a91c6f38
```

Строка: время, результат (`ok` или `fail`) и хеш адреса. Больше ничего.

- **Откуда данные.** Из журнала sshd (`journalctl -o json`, идентификаторы `sshd` и `sshd-session`). `ok` — принятый вход. `fail` — неверный ключ или пароль, неизвестный пользователь, обрыв на этапе аутентификации.
- **Хеш.** `HMAC-SHA256(секрет, логин + 0x00 + IP)`, первые 16 символов hex. Секрет лежит в `HMAC_KEY_FILE` и не покидает ноду. Логин входит в сообщение, поэтому один и тот же IP у разных клиентов даёт разные хеши, и по ним клиентов нельзя связать. IPv4 в записи IPv6 (`::ffff:a.b.c.d`) даёт тот же хеш, что обычный IPv4.
- **Сырые IP наружу не уходят.** Если формат строки не `<время> <ok|fail> <16 hex>`, бот отвергнет ответ целиком.
- **Пределы.** Период не больше 31 суток назад, не больше `LOGIN_MAX_EVENTS` событий, самые новые.

Бот хранит не больше 20 последних хешей на клиента и не дольше 30 дней. Если клиент отключает алерт «новый IP», хеши удаляются сразу.

## Снимки и восстановление

Снимки лежат в `/srv/plugbackup/<логин>/.zfs/snapshot/`. Автоматического отката нет: клиент подаёт заявку командой `/restore`, бот присылает её в админ-чат, дальше решает администратор.

Безопасный способ: не трогать текущие данные, а положить копию снимка рядом, и клиент сам выберет, чем пользоваться.

```bash
zfs list -t snapshot -r tank/clients/u1001
SNAP=/srv/plugbackup/u1001/.zfs/snapshot/<имя снимка>
cp -a "$SNAP/data/restic" /srv/plugbackup/u1001/data/restic-restored-2026-11-02
chown -R 31001:30000 /srv/plugbackup/u1001/data/restic-restored-2026-11-02
```

Клиенту: «репозиторий восстановлен по пути `/data/restic-restored-2026-11-02`». Копия занимает место в квоте клиента, при нехватке места `cp` остановится даже у root.

`zfs rollback -r` возвращает весь набор к снимку и безвозвратно теряет всё, что записано позже. Делайте это только с согласия клиента.

## Тесты

Тесты `storectl` не требуют ZFS, sudo и root: внешние программы подменены.

```bash
bot/.venv/bin/python -m pytest node/tests
```

На Windows интерпретатор лежит в `bot\.venv\Scripts\`.

## Что проверить на реальной ноде

Это допущения, которые на разработческой машине проверить нельзя:

1. Версия sshd. С OpenSSH 9.8 процесс авторизации называется `sshd-session`, оба имени учтены. Формат сообщений о неудачных входах зависит от версии, на вашей ноде сверьте их с разбором в `classify()`.
2. `zfs get -Hp` отдаёт `refquota = 0`, если квоты нет. Скрипт всегда ставит квоту, но проверьте на живом наборе.
3. `ChrootDirectory` требует, чтобы корень chroot и все его родители принадлежали root и не были доступны на запись остальным. Проверьте `ls -ld /srv /srv/plugbackup /srv/plugbackup/u1001`.
4. `pkill -KILL -u` рвёт SFTP-сессии клиента при `suspend` и `delete`. Убедитесь, что после `suspend` открытая сессия действительно закрывается.
